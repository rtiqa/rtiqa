# Blueprint System Specification

Version: 1.0

Status: Draft

---

## Overview

The Blueprint System defines a declarative, JSON-based definition format for code and artifact generation in the Rtiqa toolkit. Blueprints describe the files, directories, variables, templates, metadata, validation rules, and composition relationships required to generate a complete output artifact set. This document explains the supported blueprint fields, the validation model, merging and composition behavior, error handling, and recommended usage patterns.

## Goals

- Enable engineers to define reusable generation blueprints without reading source code.
- Provide consistent rules for inheritance, composition, dependency resolution, and rendering.
- Ensure runtime validation catches malformed blueprints early.
- Support future extension without breaking existing definitions.

## Blueprint Document Structure

A blueprint is expressed as a JSON object with the following top-level fields.

### Required fields

- `id` (string): Unique blueprint identifier.
  - Must be non-empty.
  - Used to reference the blueprint in `extends`, `compose`, and `dependencies` lists.

- `name` (string): Human-readable blueprint name.
  - Used for reporting and documentation.

- `version` (string): Blueprint version.
  - Must use semantic versioning format: `MAJOR.MINOR[.PATCH]`.
  - Allows optional pre-release or build metadata segments.

- `schema_version` (string): Blueprint schema version.
  - Must use semantic versioning format.
  - Allows compatibility validation against the engine.

### Optional fields

- `description` (string)
  - A short summary of the blueprint.

- `category` (string)
  - A label used to group or filter blueprints.

- `metadata` (object)
  - Arbitrary blueprint metadata consumed by external tooling.
  - If present, this object must conform to an optional `metadata_schema`.

- `metadata_schema` (object)
  - Describes the expected shape and data types of `metadata`.
  - Uses the same validation rules as blueprint input schema.

- `compatibility` (object)
  - Declares engine and schema version compatibility requirements.
  - Supported keys:
    - `engine` (string): engine version requirement.
    - `schema_version` (string): blueprint schema compatibility requirement.

- `outputs` (object)
  - Reserved field for future output metadata definitions.

- `schema` (object)
  - Defines input validation requirements for blueprint execution.
  - Supported sections: `required`, `optional`.

- `variables` (object)
  - Default variables that are merged with runtime inputs before rendering.
  - Can provide default values for templates and conditions.

- `conditions` (array)
  - Optional condition definitions used by code or tooling.
  - Each item is a JSON object. The engine currently preserves this list.

- `dependencies` (array of strings)
  - Lists other blueprint `id`s that must exist and be available.
  - Dependencies are validated before generation but do not imply content merge.

- `extends` (array of strings)
  - Lists blueprint `id`s whose content and configuration should be inherited.
  - Inheritance merges base blueprints into the current blueprint.

- `compose` (array of strings)
  - Lists blueprint `id`s whose content and configuration should be composed.
  - Composition merges blueprint content as if it were part of the current blueprint.

- `template_map` (object)
  - Remaps template names from referenced blueprints to alternate templates.
  - Keys are source template names; values are replacement template names.

- `directories` (array of strings)
  - Directory paths to create in the output tree.

- `files` (array of objects)
  - Defines the file artifacts generated by this blueprint.

## File Artifact Definition

Each item in the `files` array is an object with these fields.

- `path` (string): Output file path relative to the generation root.
  - Must be non-empty.
  - Absolute paths are not permitted.

- `template` (string): Name of the template to render.
  - Template paths must remain inside the configured template root.

- `variables` (object, optional)
  - Per-file variable overrides.
  - Merges with global blueprint variables and runtime inputs.

- `condition` (string, optional)
  - Conditional expression evaluated against the final render context.
  - If false, the file is skipped.

## Validation Rules

Blueprints are validated during load and before generation.

### Loader validation

The loader enforces:

- `id`, `name`, `version`, `schema_version` must be strings.
- `version` and `schema_version` must follow semantic version syntax.
- `metadata`, `metadata_schema`, `compatibility`, `outputs`, `schema`, `variables`, `template_map` must be objects.
- `conditions`, `dependencies`, `extends`, `compose`, `directories` must be arrays.
- `dependencies`, `extends`, `compose`, `directories` must contain only strings.
- `files` must be a list of objects.
- Each file object must contain non-empty `path` and `template` strings.
- File `variables` must be an object if present.
- File `condition` must be a string if present.

### Compatibility validation

At generation time, the engine validates:

- `compatibility.engine` against the current engine version.
- `compatibility.schema_version` against the blueprint's own `schema_version`.

Supported compatibility operators:

- Exact match: `1.0.0`
- Caret range: `^1.0.0` → allows versions `>=1.0.0` and `<2.0.0`
- Tilde range: `~1.0` → allows versions `>=1.0.0` and `<1.1.0`

### Schema validation

- The blueprint `schema` uses `required` and `optional` sections.
- Each field may be a simple type name or a nested object schema.
- Supported primitive type names: `string`, `integer`, `number`, `boolean`, `object`, `array`.
- Nested object schemas may include `required` and `optional` subsections.
- Validation fails if required inputs are missing or if any value does not match the expected type.

### Metadata schema validation

- When `metadata_schema` is present, the engine validates `metadata` against it.
- Uses the same type rules as input schema validation.
- This ensures metadata shape guarantees are enforced at load time.

### Dependency validation

- The engine checks that all names in `dependencies` are present in the discovered blueprint set.
- Missing dependency references cause generation failure.

## Inheritance and Composition

Inheritance and composition both merge referenced blueprints into the target blueprint. The engine resolves them recursively and merges values in deterministic order.

### Relationship semantics

- `extends` is intended for blueprint specialization and reuse.
- `compose` is intended for combining separate content units into a single output.
- Both behave similarly in the current engine and can be used interchangeably in many cases.

### Resolution order

- The engine resolves referenced blueprints depth-first.
- It merges each referenced blueprint into the current blueprint in the order listed.
- When multiple blueprints reference the same field or artifact, the later blueprint / overlay wins.

### Cycle detection

- The engine detects cycles in `extends`, `compose`, and transitive blueprint references.
- Circular references cause generation failure with a descriptive cycle path.

## Merge Precedence Rules

When merging blueprint content, the engine applies the following precedence rules from lowest to highest priority:

1. Base blueprints referenced via `extends` or `compose`.
2. Overlay blueprints later in the reference list.
3. The explicitly requested top-level blueprint.

### Field merge semantics

- Scalars and strings: overlay values replace base values.
- Objects: overlays merge with base values. In case of key collisions, overlay object members win.
- Lists:
  - `directories`, `conditions`, `dependencies`, `extends`, `compose`: combined by concatenation.
  - `files`: items are merged by `path`; later file definitions override earlier ones with the same path.
- `template_map`: later mappings override earlier mappings for the same template key.
- `compatibility`: later compatibility rules override earlier ones for the same key.
- `metadata`: merged recursively. Nested objects are merged and overlay values replace base values at the leaf level.

### Special merge behavior

- `description` and `category` are inherited from the base blueprint unless the overlay provides a non-empty value.
- `outputs` are merged shallowly, with overlay values winning.

## Variables and Inputs

Blueprint inputs are derived from three sources.

### Variable precedence

From lowest to highest priority:

1. Blueprint default `variables`.
2. Runtime inputs provided at generation time.
3. Per-file `variables`.

### Rendering context

- The engine merges blueprint-level variables and runtime inputs before rendering templates.
- Per-file variables are merged into the template context for that file only.
- The final render context is used for template interpolation and condition evaluation.

## Conditions

Blueprint file-level condition expressions are evaluated securely.

### Expression rules

- Supported operators:
  - Logical: `and`, `or`, `not`
  - Comparison: `==`, `!=`, `<`, `<=`, `>`, `>=`
  - Membership: `in`, `not in`
  - Identity: `is`, `is not`
  - Arithmetic: `+`, `-`, `*`, `/`, `%`
- Supported operand types: strings, numbers, booleans, lists, tuples, dictionaries, and variables from the render context.
- The expression is evaluated without executing arbitrary code.

### Evaluation semantics

- If a file `condition` is absent, the file always renders.
- If a condition evaluates to truthy, the file renders.
- If a condition evaluates to falsey, the file is skipped.
- Missing variables in a condition return `None` and may affect boolean logic accordingly.

## Template Mapping

Template mapping enables blueprint overlays to substitute templates used by referenced blueprints.

### `template_map`

- Maps source template names to replacement template names.
- Applies during file rendering after merge resolution.
- Example:
  - `{ "base.tpl": "alternate.tpl" }`
- The mapped template is loaded from the configured template root.

### Use cases

- Swap a default template from an inherited blueprint without editing the base blueprint.
- Apply branding or environment-specific layouts to composed content.

## Metadata

Blueprint metadata is a free-form object intended for external tooling and documentation.

### `metadata`

- May include owner, tags, labels, documentation pointers, or other structured data.
- Must be an object if present.

### `metadata_schema`

- Defines the expected shape of `metadata` using the same validation rules as blueprint input schemas.
- Helps enforce consistent metadata across the blueprint catalog.

## Version Compatibility

Blueprints may declare compatibility constraints in the `compatibility` field.

### Supported compatibility keys

- `engine`: constrains the generator engine version.
- `schema_version`: constrains the blueprint schema version.

### Version expression support

- Exact versions: `1.0.0`
- Caret ranges: `^1.0.0`
- Tilde ranges: `~1.0`

### Compatibility failure

- Generation fails if the current engine version does not satisfy `compatibility.engine`.
- Generation fails if the blueprint schema version does not satisfy `compatibility.schema_version`.

## Error Reporting

The generator reports errors at three stages.

### Load-time errors

Detected when blueprints are parsed from disk:

- Invalid JSON
- Missing required fields
- Invalid field types
- Invalid semantic version format
- Invalid file artifact format

### Resolution-time errors

Detected when blueprints are combined:

- Missing referenced blueprint in `extends`, `compose`, or `dependencies`
- Circular inheritance/composition references
- Unsupported compatibility expressions
- Metadata schema validation failures

### Validation-time errors

Detected after inputs are merged:

- Missing required input values
- Invalid input types
- Template rendering failures due to missing variables

### Reporting style

- Errors are returned as structured messages.
- Descriptive text should identify the blueprint `id`, the failing field, and the cause.
- Cycles should list the full reference chain.

## Best Practices

- Prefer small, single-purpose blueprints.
- Use `extends` only for specialization or refinement, not for unrelated content.
- Use `compose` to assemble independent pieces into a composite artifact.
- Keep `variables` as defaults, and pass environment-specific or user-specific values at generation time.
- Declare `metadata_schema` when metadata is consumed by automated tooling.
- Use file `condition` expressions for optional outputs rather than removing file entries manually.
- Avoid template path collisions by namespacing template files.
- Use `template_map` to override template variants without duplicating entire blueprints.
- Keep `dependencies` lean: only list blueprints whose presence is required but not necessarily merged.

## Future Extension Points

The current blueprint model was designed to evolve without breaking compatibility.

Potential extension areas:

- `outputs`
  - Add explicit artifact metadata, packaging targets, or output categories.

- `conditions`
  - Add named conditional groups, reusable condition definitions, or expression macros.

- `schema` enhancement
  - Support arrays, enums, and more advanced nested schema constructs.

- `metadata_schema` enhancement
  - Add full JSON Schema support or richer metadata validation.

- `dependency` semantics
  - Support optional dependencies or conditional dependencies.

- `template_map` refinement
  - Add path-based template remapping or template inheritance rules.

- `files` enhancement
  - Add file-level `mode`, `owner`, or `post_process` attributes.

- Engine extension
  - Add blueprint publishing, version negotiation, or blueprint lifecycle hooks.

## Example Blueprint

```json
{
  "id": "service-api",
  "name": "Service API Blueprint",
  "description": "Generates an API service scaffold.",
  "version": "1.0.0",
  "schema_version": "1.0",
  "category": "service",
  "metadata": {
    "owner": "platform-team",
    "tags": ["api", "service"]
  },
  "metadata_schema": {
    "required": {
      "owner": "string",
      "tags": "array"
    }
  },
  "compatibility": {
    "engine": "^1.0.0",
    "schema_version": "~1.0"
  },
  "schema": {
    "required": {
      "project_name": "string",
      "language": "string"
    },
    "optional": {
      "license": "string"
    }
  },
  "variables": {
    "license": "MIT"
  },
  "extends": ["base-service"],
  "compose": ["http-client"],
  "template_map": {
    "base-service.tpl": "service-api.tpl"
  },
  "directories": ["src", "tests"],
  "files": [
    {
      "path": "README.md",
      "template": "README.tpl"
    },
    {
      "path": "src/app.py",
      "template": "app.tpl",
      "variables": {
        "framework": "fastapi"
      },
      "condition": "language == 'python'"
    }
  ]
}
```

## Glossary

- Blueprint: A JSON definition for generation output.
- Inheritance: Reusing a blueprint by extending another blueprint's content.
- Composition: Combining multiple blueprints into one output.
- Dependency: A referenced blueprint that must be available but is not automatically merged.
- Template map: A mapping that replaces template names during rendering.
- Metadata schema: A schema that validates blueprint metadata.
- Generation root: The configured output directory where generated files and directories are written.
